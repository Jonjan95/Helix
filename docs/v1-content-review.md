# Helix v1 content review

## Review boundary

This review covers every visitor-facing sentence on the public `/` route at
the start of the v1.0 approval process. It includes semantic copy, link text,
metadata, status labels, and visible decorative interface language. It does
not review the isolated spatial lab, private planning material, or public
documentation that is not part of the portfolio journey.

The review is diagnostic. No portfolio copy has been changed. Statements that
depend on Jonathan's history, current studies, availability, or preferred
voice are marked for his input rather than rewritten by assumption.

## Editorial baseline

The current copy is careful, technically credible, and generally accurate in
its claim boundaries. It distinguishes studies and personal projects from
professional software employment, describes unfinished project scope openly,
and protects client privacy. No confirmed factual inaccuracy was found.

What keeps it from feeling personally finished is cumulative tone. The same
terms—systems, testing, quality, connected devices, problems, and verification—
appear in several introductions. Concrete first-person statements sound like
Jonathan; grouped technical nouns and process summaries sound like project
documentation. The final pass should preserve precision while giving each
chapter one distinct personal reason to exist.

## Priority definitions

- **Must fix before v1.0:** a time-sensitive claim, unclear opportunity signal,
  or release-state statement that requires confirmation before publication.
- **Should improve before v1.0:** accurate copy that is generic, repetitive,
  overly formal, or less personal than the surrounding work.
- **Optional after release:** useful depth that is not required for an honest,
  understandable first release.

## Arrival

### Must fix before v1.0

**C01 — Confirm the public identity statement.** The title says, “Software
development student with a focus on testing and quality.” Jonathan should
confirm that the study status, focus, and `Malmö, Sweden` location are still
current on the release date. This is a verification task, not a request to
inflate the title.

### Should improve before v1.0

**C02 — Supply one more personal opening thought.** “I build software projects
and explore how APIs, databases, automation, and connected devices work
together” is accurate but could describe many early-career developers. Ask
Jonathan which real experience best explains why he cares about failures
across system boundaries. Use that answer to sharpen the summary; do not invent
an origin story.

**C03 — Remove visible repetition once the opening is approved.** The same
focus appears in the frame, laptop status, eyebrow, heading, and metadata.
Repetition makes the composition feel templated even though each line is
individually clear. Keep one primary statement and let the remaining labels
provide genuinely different information.

### Optional after release

- Consider whether `Testing & quality` is Jonathan's most natural compact
  focus label after he has used the portfolio in real conversations.

## The Threshold

### Should improve before v1.0

**C04 — Review the visible system language.** `ORIENTATION / WORKSPACE`, `ENTRY
LAYER READY`, and `NATIVE SCROLL / PATH ACTIVE` are decorative and hidden from
assistive technology, but visitors still read them. `ENTRY LAYER READY` in
particular sounds provisional and generic rather than precise. Decide whether
each label explains the journey or only imitates an interface. Retain only
language with a clear narrative job.

The Threshold does not need explanatory prose. This is a restraint pass, not
an invitation to add lore or futuristic terminology.

## Environment

### Should improve before v1.0

**C05 — Make “learning by doing” specific to Jonathan.** The heading and
introduction are approachable, but “learning by doing,” “small steps,” and
“check the result” are familiar portfolio phrases. Ask Jonathan for one
ordinary example of how this changes his work—a review habit, a failed test, a
field diagnosis, or a project decision—and use only the part that clarifies
the chapter.

**C06 — Decide whether AI-assisted work belongs in the permanent identity.**
“I test ideas in real projects, document decisions, and review AI-assisted work
before using it” is responsible, but the reference can read as trend-led. Keep
it only if Jonathan considers reviewing AI output a durable part of how he
works; otherwise make the practice technology-neutral.

**C07 — Reduce semantic overlap inside each principle.** The title, summary,
`HOW I WORK` label, and practice sentence often restate one idea. Preserve the
three principles and their concrete evidence, but let each line add new
information during the approved copy pass.

## Engineering Mindset

### Should improve before v1.0

**C08 — Keep the four-step method, but earn the personal claim.** Understand,
Isolate, Observe, and Verify are the clearest and most memorable language in
the journey. The introduction currently asserts that Jonathan uses the method
across APIs, databases, devices, and field equipment without showing why it
became his method. Ask him which environment taught this most clearly and add
only enough context to make the sequence feel lived rather than invented for
the portfolio.

**C09 — Avoid another domain inventory.** The chapter introduction repeats
technical categories already named in Arrival and later repeated in
Experience. Once Jonathan supplies the personal connection, prefer that
specific reason over another list of system types.

The handoff, “The projects below show those steps at work,” is concise and
should remain the chapter's closing job.

## Selected Projects

### Must fix before v1.0

**C10 — Revalidate every status and current-scope statement on the release
commit.** `ACTIVE DEVELOPMENT`, `PROTOTYPE COMPLETE`, implemented features,
planned features, and test coverage are time-sensitive. The public repositories
can verify technical evidence, but Jonathan must confirm what he considers
current, complete, or intentionally deferred.

**C11 — Replace Helix's pre-release boundary at the point of release.** The
Helix entry currently says that project media, interactive nodes, final visual
polish, and possible 3D work remain later. That is honest during development,
but “final visual polish remains later work” directly conflicts with approving
v1.0. At release, describe the actual v1 boundary and move speculative future
work out of the main case study.

### Should improve before v1.0

**C12 — Translate architecture prose into visitor outcomes where possible.**
Phrases such as “provider-neutral AI integration,” “Zod-validated contracts,”
“immutable run events,” and “one responsive JourneyMotion owner” are precise,
but several paragraphs read like repository documentation. Preserve concrete
technologies and claim boundaries; shorten or reframe only where the detail
does not help a visitor understand the problem, decision, or quality of the
result.

**C13 — Give each project a distinct human reason.** The Problem/Approach/
Technical work/Checks structure is credible but mechanically uniform. Ask
Jonathan why he chose each project and what surprised him. One verified detail
per project would create more voice than a broad rewrite.

Project names, status honesty, repository links, and the explicit separation
between working and planned functionality should be preserved.

### Optional after release

- Deeper case-study routes can carry implementation detail if the overview is
  intentionally shortened later.
- Longer lessons-learned narratives belong in those routes, not in the main
  journey.

## Experience

### Must fix before v1.0

**C14 — Confirm the education wording and ongoing status.** “Studying systems
development with a focus on QA and test automation” should match the official
programme wording closely enough to be unambiguous. Jonathan should provide or
approve the programme name, school, current status, and any date range he wants
public. Do not imply completion.

**C15 — Confirm the safe boundary for technical-service evidence.** The current
copy responsibly avoids client names and confidential details, but Jonathan
should approve the descriptions of field work, independence, equipment checks,
component replacement, and escalation before v1.0. Employer, title, and broad
timeframe should be added only if verified and intentionally public.

### Should improve before v1.0

**C16 — Add one grounded anchor to each experience track.** The three-track
narrative is stronger than a CV timeline, but broad timeframes such as `CURRENT
STUDIES AND PROJECTS` and `PRACTICAL FIELD EXPERIENCE` make the evidence feel
less situated. A verified programme, project, role, or broad period would make
each track more credible without creating an employment-history dump.

**C17 — Reduce repeated lessons.** “Understand the problem,” “narrow the
cause,” and “check the result” repeat the Engineering sequence almost exactly.
Experience should show where the habits came from; Engineering should name the
method. Preserve that division in the copy pass.

## Continue

### Must fix before v1.0

**C18 — Clarify and date the opportunity signal.** `LIA` is not explained for
visitors outside Swedish vocational education, and the availability statement
will expire. Jonathan should confirm the intended LIA period, whether junior
roles are currently relevant, preferred role families, location/remote
boundaries, and the plain-English wording he wants public. Do not publish an
availability date by guessing.

**C19 — Reconfirm all contact routes.** GitHub and LinkedIn are verified public
routes. The Hotmail address is functional, but Jonathan should explicitly
choose whether it remains the professional contact address for v1.0 or is
replaced by a public address on a personal domain.

### Should improve before v1.0

**C20 — Replace generic closing language with Jonathan's natural invitation.**
“If my work or background connects with what you are building” and “thoughtful
technical collaboration” are polite but abstract. Ask what conversations he
actually wants to receive and use direct language. Keep the tone restrained;
this should not become a sales pitch.

`The path remains open.` is concise, fits the concept, and does not need more
explanation.

## Global consistency

### Should improve before v1.0

**C21 — Run one approved voice pass after the factual decisions.** The pass
should remove repeated domain lists, reduce documentation syntax, and prefer
concrete first-person verbs. It must not change study, employment, project, or
privacy claims without Jonathan's approval.

**C22 — Keep terminology deliberate.** Choose one public form for software
development/systems development, testing/QA/quality engineering, and LIA/
internship, then use variants only when they mean different things. Technology
names can remain exact.

### Optional after release

- A Swedish-language version, downloadable CV, and extended biography are
  separate product decisions, not missing copy for the English v1 journey.
- Social proof, testimonials, metrics, and client names should remain absent
  unless verifiable evidence and publication approval exist.

## Finite content path to v1.0

1. Jonathan answers the six questions above.
2. Verify project claims against the release commit and public repositories.
3. Approve a targeted copy patch for C01–C22; do not perform an unrelated
   rewrite.
4. Re-read the rendered page once for repetition and once for factual accuracy.
5. Record final human sign-off for identity, education, work history,
   availability, project status, privacy, and contact routes.

Content is ready for v1.0 when those five steps are complete. New chapters,
long-form biography, a CV, and deeper case studies are not prerequisites.
